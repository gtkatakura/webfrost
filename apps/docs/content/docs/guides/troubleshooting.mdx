Run with `WEBFROST_LOG_LEVEL=debug` (or `--verbose` on the CLI) first. Debug output shows each extractor's duration, failures, and why a fetch failed.

## Snapshot has no PDF, screenshot, DOM snapshot or SingleFile

**Cause:** Chromium is missing or not found, navigation failed, or a request hit the SSRF policy. Those four extractors are recorded as failed, and the snapshot still ends `done` with WARC, Readability and HTML.

`GET /api/v1/snapshots/:id` shows each failure as `status: "failed"` with an `error` in `extractorMeta`. Read the message.

**Fix:**

```bash
webfrost doctor    # is a Chromium found, and which one
webfrost setup     # install a headless Chromium if none is
# or use a browser you already have
export WEBFROST_CHROMIUM_PATH=/usr/bin/chromium
```

The Docker image already bundles Chromium. A message starting with `blocked:` means the page redirected to a private address: see [Security](/docs/architecture/security#ssrf-protection).

## No media for a YouTube or Vimeo URL

**Cause:** `yt-dlp` is not installed, or the URL is not a media page. Media extraction is then skipped silently and no failure is recorded. The Docker image bundles `yt-dlp` and ffmpeg.

**Fix:** install it (`brew install yt-dlp`, `sudo apt install yt-dlp` or `pipx install yt-dlp`, see [Install](/docs/getting-started/install#yt-dlp-and-ffmpeg)) and make sure `yt-dlp` is on `PATH`; `webfrost doctor` checks it. If a media page yields metadata but no media file, the download may have exceeded the 500 MB cap or failed; check the debug log.

## Snapshots stay `pending` or end `failed`

A snapshot is `pending` while it waits in the job runner or runs. The runner executes at most `WEBFROST_CONCURRENCY` pipelines (default 3), and archives of the same host start about `WEBFROST_DOMAIN_DELAY_MS` apart (default 1000 ms), so a burst queues up.

A snapshot ends `failed` when:

- the page could not be fetched: a timeout (`WEBFROST_FETCH_TIMEOUT_MS`, default 30 s), a network error, a certificate the runtime does not trust, or an SSRF block;
- the server answered with an HTTP status of 400 or higher (the browser is not tried after that);
- no extractor produced output;
- it was interrupted three times and given up on.

After a crash or restart, snapshots left `pending` are re-queued automatically: a snapshot is adopted once its lease (45 seconds) has expired, at the next recovery sweep, which runs at startup and every minute. Give it a minute or two.

**Fix:** raise `WEBFROST_CONCURRENCY` if the machine can take it, check the log for the failure reason ([the next section](#a-page-opens-in-my-browser-but-its-snapshot-fails) explains the common ones), and set `WEBFROST_ALLOW_PRIVATE_URLS=true` only if you really intend to archive intranet addresses.

## A page opens in my browser, but its snapshot fails

WebFrost fetches the page over plain HTTP before it opens the browser, and a failed fetch ends the snapshot (see [the pipeline](/docs/architecture/pipeline)). The log names the reason: `fetch failed snapshot=<id>: <reason>` when no answer came, `fetch error snapshot=<id> status=<code>` when the server answered with an error. Three reasons account for nearly all of them.

### The page is gone

**Log:** `getaddrinfo ENOTFOUND` (the domain no longer exists), `status=404` or `status=410`, a timeout on a host that never answers.

Expected when you import years of bookmarks: a large share of old links are dead, and a browser that seems to open one is often showing a cached copy or a parked domain. Nothing to fix. `webfrost list --status failed` shows them.

### `unable to get local issuer certificate`

**Cause:** the site's certificate comes from a certificate authority that browsers already trust and the runtime does not yet. The fetch checks certificates against the list of roots built into the Bun that WebFrost runs on; Chromium brings its own, newer list. When an authority starts issuing under a new root, there is a period in which the browser opens the page and the fetch refuses it. At the time of writing this is the case for the roots Let's Encrypt created in 2025 (Root YE and Root YR): a growing number of sites use them.

**Fix:** give the fetch the missing link of the chain with `NODE_EXTRA_CA_CERTS`, a file of PEM certificates that are added to the built-in roots. It works for the binary and for the Docker image. Let's Encrypt publishes both new roots signed by its older ones, which every list has, so nothing new has to be trusted on faith:

```bash
curl -fsSO https://letsencrypt.org/certs/gen-y/root-ye-by-x2.pem
curl -fsSO https://letsencrypt.org/certs/gen-y/root-yr-by-x1.pem

# Both must print "OK": each one chains to a root your system already trusts.
openssl verify root-ye-by-x2.pem root-yr-by-x1.pem

cat root-ye-by-x2.pem root-yr-by-x1.pem > extra-ca.pem
```

Then start WebFrost with the variable set, and archive the failed pages again:

```bash
NODE_EXTRA_CA_CERTS=$PWD/extra-ca.pem webfrost serve

# Docker: mount the folder that holds the file, read-only
docker run -v $PWD:/etc/webfrost-ca:ro -e NODE_EXTRA_CA_CERTS=/etc/webfrost-ca/extra-ca.pem ...
```

The file is read once, at start. If it is missing, a warning is printed and WebFrost runs without it. For another authority the steps are the same with its certificates; prefer, as here, a certificate signed by a root you already trust over a new self-signed root. Do not turn certificate checking off instead: the archive would then record whatever anyone on the path chose to send. The variable can go once a WebFrost release ships a runtime that has the roots.

### The site refuses the visit: `status=403`, `status=429`, a reset connection

**Cause:** the site, or the protection service in front of it, turns away visitors it takes for automated ones. There are two kinds of refusal, and only one is about how WebFrost presents itself:

- **By what the client looks like.** Some servers drop any client that does not send a browser's headers. WebFrost sends the headers of a Chrome navigation on every fetch, so these sites answer.
- **By where the visit comes from.** Many large sites and most protection services judge the address: connections from the ranges of hosting providers and data centres get `403`, `429` or a "checking your browser" page, whatever the client. A browser on your own computer opens the same page because it arrives from a home or office connection. Changing headers does nothing here, and the headless browser is turned away the same way.

**What to do:** WebFrost has no setting for the second kind. The page archives from a machine on a home or office connection (WebFrost on your own computer, or a home server), or from a public address of the same content that is not behind the protection. A `429` can also be plain rate limiting: archive that site's pages again later, and raise `WEBFROST_DOMAIN_DELAY_MS` to space them out.

## Login bounces back to the login page

**Cause:** the session cookie is `Secure`, and browsers drop it on plain-HTTP origins other than `localhost`. Typical when opening `http://<lan-ip>:3000`.

**Fix:** serve WebFrost over TLS, or for an HTTP-only deployment set `WEBFROST_INSECURE_COOKIES=true`.

## `429 Too Many Requests`

**Cause:** the API limits requests per client IP (see [Rate limits](/docs/reference/rest-api#rate-limits)). Behind a reverse proxy every client shares the proxy's address unless `WEBFROST_TRUST_PROXY=true`.

**Fix:** wait for the `Retry-After` period, and set `WEBFROST_TRUST_PROXY=true` behind a proxy that overwrites `X-Forwarded-For`.

## Server exits with `SESSION_SECRET env var is required`

The Docker image refuses to start without `SESSION_SECRET` unless `AUTH_DISABLED=true`, and `compose.yml` refuses to start until it is set in `.env`. (`webfrost serve` generates one instead.)

```bash
export SESSION_SECRET=$(openssl rand -hex 32)
```

A secret shorter than 32 characters starts, with a warning.

## Schedules do not run

**Cause:** the scheduler is off (`WEBFROST_SCHEDULER=false`) and no `webfrost schedule worker` is running, or the cron expression is evaluated in a different time zone than you expect. The time zone is `TZ`, which is UTC in Docker.

**Fix:** remove `WEBFROST_SCHEDULER=false` or start a worker, and set `TZ`. A schedule whose previous run is still going waits until it ends.

## Downloads fail with 403 or "file not found"

**Cause:** the file reference stored in the database no longer matches the storage in use. This happens after switching `WEBFROST_STORAGE_BACKEND`, after moving the data directory to a different absolute path, or when a relative `WEBFROST_DIR` is used from a different working directory.

**Fix:** use an absolute `WEBFROST_DIR` and keep it stable. See [Storage](/docs/guides/storage#switching-backends-on-an-existing-archive).

## `database is locked`

**Cause:** several processes write to one SQLite database. Connections wait up to 5 seconds for a competing writer, so a server plus CLI commands or a schedule worker on one archive is fine. The error appears when a writer is blocked longer, or after an unclean shutdown.

**Fix:** look for a stuck process holding the database open. If it persists after a clean shutdown, checkpoint the write-ahead log:

```bash
sqlite3 ~/.webfrost/archive.db "PRAGMA wal_checkpoint(TRUNCATE);"   # or $WEBFROST_DIR/archive.db
```

Do not do this while [Litestream](/docs/guides/backups#continuous-backups-with-litestream) replicates the archive: stop Litestream first, and let it take a fresh snapshot afterwards. With many writers on one archive, PostgreSQL or MySQL (`DATABASE_URL`) avoids the single-writer lock altogether.

## Search finds nothing after an import

The full-text index may be out of sync. Rebuild it:

```bash
webfrost search:rebuild
```

Only snapshots that finished `done` are indexed.

## `webfrost: command not found`

The installer puts the binary in `~/.local/bin`, which is not on every `PATH`. Add it (`export PATH="$HOME/.local/bin:$PATH"` in your shell profile) and open a new terminal, or install somewhere else with `WEBFROST_INSTALL_DIR`. See [Install](/docs/getting-started/install).

## `webfrost doctor` reports no Chromium

Run `webfrost setup`. It installs a headless Chromium into WebFrost's cache directory, unless it finds one. If setup or doctor says the browser does not start, or cannot open a page, a system library is missing: they print the command that installs what it needs on your distribution; run it and then `webfrost setup` again. Installing Chromium from your package manager (`apt install chromium`) works too. A `WEBFROST_CHROMIUM_PATH` that points at a missing file is an error on purpose; unset it or fix it.

## `Unknown command: --verbose`

`--verbose` and `--quiet` go after the command: `webfrost add https://example.com --verbose`. You can also set `WEBFROST_LOG_LEVEL=debug`.

## Authenticated pages

**Symptom:** a page you can read while signed in is archived as its login page, an error page or a paywall.

**Cause:** WebFrost archives every page as an anonymous visitor. Each snapshot gets a fresh headless Chromium context with no stored session, and there is no way yet to pass it cookies, a browser profile or custom headers (`Authorization` included), from the CLI, the API or the web UI. `WEBFROST_CHROMIUM_PATH` changes which Chromium binary runs, never its profile.

**What to do instead:**

1. **Archive a public address of the same content**, if there is one: a share link, a public export, a print or cached view.
2. **Save the page yourself** while signed in, for example with the SingleFile browser extension, and keep the file next to your archive. WebFrost cannot import such a file yet.
3. **Follow the roadmap**: cookie and browser-profile support is tracked in [ROADMAP.md](https://github.com/gtkatakura/webfrost/blob/main/ROADMAP.md).

Pages on your own network are a different limitation: private, loopback and link-local addresses are blocked unless `WEBFROST_ALLOW_PRIVATE_URLS=true`. See [SSRF protection](/docs/architecture/security#ssrf-protection).
