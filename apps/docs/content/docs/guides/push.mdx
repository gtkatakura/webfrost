Your server is where the archive lives, but it is not always the best place to archive from. The common case is video: YouTube and other video sites often refuse requests from server and data-center addresses ("Sign in to confirm you're not a bot"), so the `media` extractor fails on the server while the same video downloads fine from your home connection. It also helps when you are on a laptop and want everything kept in one place.

`webfrost push` covers both: archive with the CLI where it works, then send the finished snapshot to the server. The server stores it as a new snapshot, with the same files (video included), results, tags and capture time, as if it had archived it itself. It does not fetch anything again.

## Before you start

- The `webfrost` CLI on your machine ([install](/docs/getting-started/install)), with `yt-dlp` on `PATH` for videos (`webfrost doctor` checks).
- An API key of the server: in the web UI, **Settings → API keys → Create**, or on the server `webfrost admin key create --name laptop`. The key is shown once.

## Archive and push

```bash
# 1. Archive locally, into ~/.webfrost on your machine
webfrost add https://www.youtube.com/watch?v=...
# Snapshot 12 done ...

# 2. Connect to the server (once per machine: it opens the server's web UI for you to approve)
webfrost login https://archive.example.com

# 3. Send it
webfrost push 12 --to https://archive.example.com
# Pushed snapshot 12 (73.4 MB): snapshot 57 on https://archive.example.com, done
```

Snapshot 57 now shows up in the server's web UI and search, with the video, its poster and every other format. Ids are per archive, so the server's id differs from your local one. Push several at once with `webfrost push 12 13 14 --to ...`; add `--json` for a result per snapshot.

Use an `https` URL. Plain `http` is refused unless the server is on this machine, or you pass `--insecure` for a network you trust (a home LAN, a VPN), since the key and the snapshot would travel unencrypted.

[`webfrost login`](/docs/reference/cli#webfrost-login-server) asks the server for an API key of its own: it shows a short code and opens the server's web UI, where you approve the request that shows the same code. The key is saved in a file only you can read and is listed on the server under Settings, API keys, where you can revoke it (or run `webfrost logout`). If the server is only reachable on a private network, or sits behind a proxy with its own sign-in, see [how the command line reaches it](/docs/reference/cli#a-server-behind-a-proxy-or-on-a-private-network). In a script or CI, set `WEBFROST_API_KEY` to a key created in Settings instead; a key is never taken from a command-line flag, so it does not land in your shell history or in the process list.

Your local copy stays where it was. Remove it with `webfrost delete 12` once the push succeeded, if you do not want to keep it.

## Many failed pages at once

When the server could not archive many pages, typically the **Blocked by the site** group in [Review failures](/docs/reference/web-ui#review-failures) (a site that refuses data-center addresses), `webfrost rescue` does the archive-and-push for every one of them, and swaps each failure for the copy that worked:

```bash
webfrost login https://archive.example.com   # once, if this machine is not connected yet
# What would be tried, per domain
webfrost rescue blocked --from https://archive.example.com --dry-run
# One domain first, to see how it goes
webfrost rescue blocked --from https://archive.example.com --host www.example.com
# Then the rest
webfrost rescue blocked --from https://archive.example.com
```

For each failed snapshot it archives the page here, in a scratch archive of the run (`rescue/run-*/` in the data directory, not your own archive), and checks the copy before anything is sent:

- It must have finished `done`, with the browser formats (screenshot, PDF, DOM): Chromium has to work on this machine (`webfrost doctor`). A page that fails here too stays as it is on the server.
- It must be the page itself, both as fetched and as the browser rendered it. A copy whose title or first lines are an anti-bot interstitial ("Just a moment...", "Client Challenge", "Access Denied" and the like, including one a script puts up after the page loads), or that has almost no text (a login wall, a cart page), or that was redirected to a sign-in page or to the home page, is **not sent**: it would look like a success and hide the failure. PDFs and other downloads go as they are.
- A page that answers 404 here, or a domain that does not resolve, is reported as really gone; trash it in Review failures.

The copy that passes is sent with the id of the failure it replaces. The server stores it, carries over the failure's tags and moves the failure to the trash in one transaction, and only while that snapshot is still a failure of the same URL: if it was retried, archived or trashed in the meantime, the copy is refused and nothing is stored. So running `rescue` again, after a Ctrl+C or a crash, carries on with what is left and never stores a page twice.

A site that refuses this machine as well is not asked hundreds of times: after three failures in a row on a domain (`--give-up-after`) the rest of it is skipped and reported as not tried. Some anti-bot checks refuse any automated browser, wherever it runs; those pages stay in the group. Each page runs every extractor, so expect tens of seconds per page; `--concurrency` works on more domains at once, one page at a time per domain. Every option: [`webfrost rescue`](/docs/reference/cli#webfrost-rescue-group---from-url).

## Without push

A snapshot can travel as a file too. `webfrost export 12 -o talk.zip` writes a **snapshot bundle**: one ZIP with the snapshot's files and a `manifest.json`. Then either:

- copy it to the server's machine and run `webfrost import talk.zip` there (with the server's `WEBFROST_DIR`), or
- upload it yourself: `curl -X POST https://archive.example.com/api/v1/snapshots/import -H "Authorization: Bearer $WEBFROST_API_KEY" -H "Content-Type: application/zip" --data-binary @talk.zip`.

See [the import route](/docs/reference/rest-api#import-a-snapshot-bundle) for the format.

## Large videos

The server accepts bundles up to `WEBFROST_IMPORT_BUNDLE_MAX_BYTES` (default 2 GiB), checked both as uploaded and once decompressed. It streams the upload to `WEBFROST_DIR/tmp` before storing it (in S3 too, when that is the backend), so that disk needs room for the largest bundle.

A reverse proxy or tunnel in front of the server often has its own, lower upload limit (nginx `client_max_body_size` defaults to 1 MB, and some CDNs cap request bodies at 100 MB). If push fails with `HTTP 413`, raise the proxy's limit, or push from inside your network to the server's own address.

## What the server checks

A bundle is an upload of files, so the server treats it as untrusted: the manifest must match the format exactly, extractor names come from a fixed list, every file has a fixed name (no paths), every file in the ZIP must be referenced, and sizes are capped before and while decompressing. The server decides where files are stored and which content type they are served with; archived HTML is shown only through the sandboxed preview, as for any snapshot. A bundle that breaks a rule gets `400` and nothing is stored. Details: [Security](/docs/architecture/security#snapshot-bundles).
