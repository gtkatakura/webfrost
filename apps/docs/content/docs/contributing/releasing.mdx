WebFrost uses [Semantic Versioning](https://semver.org/) and [changesets](https://github.com/changesets/changesets) for version bumps and the changelog. All packages move together.

## Versioning policy

`MAJOR.MINOR.PATCH`:

| Change | Bump |
|---|---|
| Breaking API or CLI change, incompatible database migration | **MAJOR** |
| New feature, CLI command or server route, backwards-compatible | **MINOR** |
| Bug fix, docs, dependency update, performance tweak | **PATCH** |

When in doubt, use PATCH. Prefer MINOR over MAJOR: WebFrost is self-hosted, so users control their own upgrades.

All packages (`@webfrost/core`, `@webfrost/cli`, `@webfrost/server`, `@webfrost/sdk`, `@webfrost/ui`) share one version number through a `fixed` group in `.changeset/config.json`. Private packages are versioned with the group but get no per-package tag (`privatePackages.tag: false`), and `@webfrost/docs` is ignored. Versions stay on `0.x` until the maintainers decide to release `1.x`.

Pre-release suffixes for a tag:

| Suffix | Meaning |
|---|---|
| `-alpha.N` | Incomplete, not ready for broad testing |
| `-beta.N` | Feature-complete, may have known issues |
| `-rc.N` | Release candidate, ships unless a blocking bug appears |

Example: `v0.2.0-alpha.1`, `v0.2.0-rc.1`, `v0.2.0`.

## Add a changeset

Every pull request that changes behavior users will notice needs one:

```bash
bun changeset
# pick the bump type and write a short description
```

Commit the generated `.changeset/*.md` file with the pull request.

## Cut a release

<Steps>
<Step>

### Make sure `main` is green

All intended pull requests are merged and CI passes on `main`.

</Step>
<Step>

### Merge the Version Packages pull request

When changesets accumulate on `main` and CI has passed, the **Changesets** job of the release workflow opens or updates a pull request titled `chore: version packages`. It bumps every package version and writes the `CHANGELOG.md` entries. Review and merge it.

<Callout type="warn" title="CI does not run on that pull request by itself">
Workflows do not start for pull requests opened or updated with the built-in `GITHUB_TOKEN`, so the required checks never report and the pull request cannot be merged. Close and reopen the pull request: the reopen event comes from you, so CI runs. Do this after every update of the pull request. If it becomes tedious, switch the action to a GitHub App token.
</Callout>

```bash
gh pr list --search "chore: version packages"
```

</Step>
<Step>

### Tag the release

```bash
NEW_VERSION=$(node -p "require('./packages/core/package.json').version")
git tag "v$NEW_VERSION"
git push origin HEAD "v$NEW_VERSION"
```

Pushing a `v*.*.*` tag triggers the release workflow, which checks that CI passed for that commit and then builds and pushes the multi-arch Docker image. Tag a commit on `main` that CI has already passed.

</Step>
<Step>

### Check the GitHub release

The workflow creates the release itself: the five binaries, `checksums.txt` and the notes from the `CHANGELOG.md` section of the version (GitHub-generated notes when there is none). A tag with a suffix (`-rc.1`) is a pre-release, never "latest", and does not touch Homebrew.

```bash
gh release view "v$NEW_VERSION"
curl -fsSL https://webfrost.dev/install.sh | WEBFROST_VERSION=$NEW_VERSION sh
```

</Step>
<Step>

### Smoke test the image

```bash
docker run --rm -d --name wf-smoke -p 3001:3000 \
  -e SESSION_SECRET=$(openssl rand -hex 32) \
  ghcr.io/gtkatakura/webfrost/server:$NEW_VERSION
sleep 5 && curl http://localhost:3001/health   # {"status":"ok"}
docker stop wf-smoke
```

</Step>
</Steps>

### Hotfix

For an urgent fix, branch from the broken tag (`git checkout -b hotfix/v0.1.1 v0.1.0`), apply the minimal fix with a changeset, merge to `main` through a pull request, merge the Version Packages pull request, then tag and push.

### Roll back

Deploy the previous image tag, and restore a backup first if the release changed the database schema. See [Deploy](/docs/guides/deploy#roll-back).

## CI

`.github/workflows/ci.yml` runs on every pull request and push to `main`:

| Job | What it does |
|---|---|
| Lint | `bun run lint` (Biome) |
| Typecheck | `bun run typecheck`, then `bun run build` to keep the quickstart working |
| Unit Tests | `bun run test`, with Playwright Chromium and a MinIO container for the S3 integration tests |
| Server API E2E | `bun run test:e2e` in `packages/server` |
| E2E | Playwright tests in `packages/ui`, with Chromium and yt-dlp, `AUTH_DISABLED=true`. Traces upload on failure. |
| Docker build | Builds `packages/server/Dockerfile` and `apps/docs/Dockerfile` without pushing, so a broken Dockerfile fails the pull request |

Each job installs with `bun install --frozen-lockfile` and caches Bun's package cache. CI has read-only permissions (`contents: read`).

Benchmarks are not part of CI. `.github/workflows/bench-vs-archivebox.yml` runs the microbenchmarks and the ArchiveBox comparison weekly (Mondays 05:00 UTC) and on manual dispatch. Results upload as artifacts for 90 days.
## Release workflow

`.github/workflows/release.yml` runs on `v*.*.*` tags, after a successful CI run on `main`, and on manual dispatch (target `docker-ghcr`).

| Job | Runs when | What it does |
|---|---|---|
| CI gate | tag or dispatch | Fails unless the commit already has a successful CI run. It does not run the tests again. |
| Changesets | CI succeeded on `main` | Creates or updates the `chore: version packages` pull request. When that pull request is merged, it publishes to npm with `changeset publish`, using npm trusted publishing (OIDC) with provenance. |
| Docker to GHCR | tag or dispatch, after the gate | Builds `packages/server/Dockerfile` for `linux/amd64` and `linux/arm64` (QEMU and Buildx) and pushes `ghcr.io/gtkatakura/webfrost/server`. Layers are cached in GitHub Actions. |
| Binaries | tag | `bun build --compile` for `darwin-arm64`, `darwin-x64`, `linux-x64`, `linux-arm64` and `windows-x64` on one Linux runner (Bun cross-compiles), with the UI embedded and the tag as the version. Packs `webfrost-<os>-<arch>.tar.gz` (`.zip` for Windows) and `checksums.txt` (SHA-256). |
| Verify binary | after Binaries | Runs `--version`, `--help`, `init`, `list` and `doctor` from the archives on Linux, macOS (arm64) and Windows. A failure stops the release. |
| GitHub Release | after Verify binary | Creates the release for the tag (or uploads to it) with the archives and `checksums.txt`. `install.sh`, `install.ps1` and the Homebrew formula read these file names. |
| Homebrew tap | after GitHub Release, stable tags only | Writes `Formula/webfrost.rb` (URL and SHA-256 per OS and CPU) to `gtkatakura/homebrew-tap` and pushes it. Skipped, passing, when the `HOMEBREW_TAP_TOKEN` secret is not set. |
| Visual verify | after the Docker job | Starts the pushed `sha-<short-sha>` image with `AUTH_DISABLED=true`, waits up to 60 s for `/health`, runs a Playwright check that the page renders without console errors, and uploads a screenshot as `deploy-screenshot-<sha>` for 90 days |

Image tags: `<version>` and `<major>.<minor>` (no leading `v`) and `sha-<short-sha>` on a version tag, plus `latest` on a stable tag (a tag with a `-rc.1` style suffix does not move `latest`). A merge to `main` alone does not build an image.

If **Visual verify** fails, open the `deploy-screenshot-<sha>` artifact: a blank page or an error state is obvious. Usual causes are a static asset build failure (blank page), a JavaScript error, or a slow start (health timeout).

### Enabling npm publishing

Packages are `"private": true` today (except `@webfrost/sdk`, which is not), so `changeset publish` publishes at most that one. To publish, set `"private": false` in each package to release and register the repository as a trusted publisher for each package on npmjs.com (package settings, Trusted Publisher, workflow `release.yml`). No `NPM_TOKEN` secret is needed: the job has `id-token: write` and `NPM_CONFIG_PROVENANCE=true`.

### Secrets and permissions

| Item | Purpose |
|---|---|
| `GITHUB_TOKEN` | Injected automatically; pushes to GHCR and opens the Version Packages pull request |
| npm trusted publisher | Replaces an npm token; configured on npmjs.com, not in the repository |
| `HOMEBREW_TAP_TOKEN` | Repository secret. A fine-grained personal access token with **Contents: Read and write** on `gtkatakura/homebrew-tap` and nothing else. Without it the release still succeeds and the formula is not updated. |

In repository settings, under Actions, allow workflows to create pull requests, and make the `ghcr.io/gtkatakura/webfrost/server` package public after the first push.
